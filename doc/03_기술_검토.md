# 03. 기술 검토

## 1. 구현 방식 비교

| 방식 | 설명 | DRM 콘텐츠 | 4K | 유지보수 | 판단 |
|------|------|:---:|:---:|:---:|:---:|
| **A. WebView2로 공식 웹 플레이어 호스팅** | 앱 안의 Edge(Chromium) 브라우저로 각 서비스 웹사이트를 띄움 | 가능 (PoC 통과: Netflix·TVING·Wavve 3/3 재생) | 서비스별로 다름 | 좋음 | **채택** |
| B. CefSharp (CEF) | 오픈소스 Chromium 임베딩 | Widevine CDM 라이선스·서명 문제로 사실상 불가 | 낮음 | 보통 | 제외 |
| C. 스트림 URL 직접 재생 (LibVLC, FFmpeg 등) | 서비스 API에서 스트림 주소를 얻어 네이티브 플레이어로 재생 | 불가(DRM 우회 필요, 불법) | - | 나쁨(비공식 API) | **제외** |
| D. 공식 앱 실행기 (런처) | 각 서비스의 공식 앱/브라우저를 실행만 함 | 가능 | 가능 | 좋음 | **제외** (D-07: 외부로 넘기면 앱을 쓸 이유가 없음) |

**결론**: **A(WebView2)만 씁니다. 모든 재생은 앱 안에서 하고, 외부 실행 대체 경로는 두지 않습니다(D-07).** WebView2에서 안 되는 것은 서비스가 허용하는 범위 안에서 최대 화질로 보거나, 지원 목록에서 제외합니다.

> 참고: 치지직과 YouTube는 DRM이 없어서 C 방식(예: HLS 직접 재생)도 기술적으로 가능합니다. 하지만 비공식 API 의존, 약관 문제, 채팅 등 웹 기능이 빠지는 문제가 있어 1차 범위에서는 제외합니다.

## 2. DRM 분석 (최대 리스크)

### 2.1 DRM 기술 요약

| DRM | 제공사 | 주요 사용처 | 보안 수준과 해상도 |
|-----|--------|-------------|-------------------|
| Widevine | Google | Chrome, Edge, Android | L3(소프트웨어): 보통 720p~1080p까지 / L1(하드웨어): Windows PC 브라우저에서는 사실상 없음 |
| PlayReady | Microsoft | Edge, Windows 앱, Xbox | SL2000(소프트웨어) / **SL3000(하드웨어, 4K에 필요)** |

### 2.2 WebView2와 DRM

- WebView2는 Microsoft Edge(Chromium) 엔진이라 Edge 브라우저와 같은 DRM 지원을 **기대할 수 있습니다**. 다만 이번 조사에서 **WebView2 임베디드 환경에서 Widevine/PlayReady 지원을 확인해 주는 공식 문서는 찾지 못했습니다.**
- Microsoft Teams(WebView2 기반)에서 DRM 지원이 따로 요청되었던 사례가 있어, 런타임 버전이나 설정에 따라 DRM 동작이 다를 수 있습니다.
- 따라서 **"WebView2에서 Netflix/TVING/Wavve가 재생되는가"는 프로젝트 성립을 좌우하는 핵심 가정이었고, Phase 0 PoC에서 가장 먼저 검증했습니다.**
- **PoC 실측(2026-10-13)**: EME 조회 결과 WebView2(런타임 154)에 **Widevine L3(SW_SECURE_DECODE)** 와 **PlayReady 보안 수준 3000(하드웨어)** 이 모두 있고, HEVC 10-bit 4K HDR·AV1·VP9 하드웨어 디코딩도 지원합니다. Edge 브라우저와 같은 구성입니다([09 PoC 결과](09_PoC_결과.md) 4.3절). 실제 서비스 재생도 로그인 후 **Netflix 1080p, TVING 1080p, Wavve 720p(1080p 선택 가능 여부 미확인)로 3/3 성공**했습니다([09 PoC 결과](09_PoC_결과.md) 3절).

### 2.3 Netflix 4K 요구사항 (알려진 조건)

과거 자료 기준이므로 최신 Netflix 고객센터 정보로 다시 확인해야 합니다.

- Microsoft Edge 브라우저 또는 Netflix Windows 앱
- PlayReady 3.0(SL3000, 하드웨어 DRM)
- 10-bit HEVC 하드웨어 디코딩(Windows용 HEVC 확장 필요)
- 모든 연결 디스플레이가 **HDCP 2.2** 지원
- 프리미엄 요금제, 약 25Mbps 이상 회선

→ **WebView2 안에서 Netflix 4K는 불가능하거나 매우 불확실**합니다. PoC에서 Netflix는 **1080p로 재생**됐고(1080p 모니터 기준, 4K 디스플레이 실측은 미완), 외부 실행으로 대체하지 않고(D-07) 앱 안에서 서비스가 허용하는 최대 화질로 봅니다. 설정 > 정보의 DRM 진단 화면에서 현재 환경의 한계를 안내합니다(Phase 3 설정 화면에서 구현 예정. PoC의 EME 조회 스크립트는 `src/MoaView.App/Scripts/drm-probe.js`로 보존).

**"4K 지원"의 정의 (제안)**:
> 앱은 4K 디스플레이에서 원본 해상도로 렌더링하고 하드웨어 디코딩을 쓴다. 실제 스트림 해상도는 각 서비스의 DRM, 요금제, 코덱 정책을 따르며, 앱은 각 서비스가 허용하는 최대 화질을 받을 수 있는 환경을 제공한다.

### 3.1 치지직 그리드(P2P)와 고화질 조건 (2026-10-13 조사)

치지직은 PC 브라우저에서 고화질로 보려면 **그리드(P2P 전송)** 를 설치해야 합니다. 그리드는 두 부분으로 되어 있습니다.

| 구성 | 내용 |
|------|------|
| 브라우저 확장 프로그램 | Chrome·Edge·Whale용. 치지직 페이지에서 설치 안내가 뜸 |
| 네이버 라이브 스트리밍 커넥터 | 별도 설치하는 Windows 데스크톱 프로그램(Windows 10 이상, Mac 미지원). 확장과 통신해서 P2P 전송을 담당 |

**확인된 사실**

- 2024년 5월 2일부터 순차 적용. 당시 보도로는 그리드를 설치하지 않으면 480p로 제한되고 720p60·1080p60은 그리드가 있어야 한다고 했으나, 2026-10-13 PoC 실측은 그리드 없이 **720p**였습니다(아래).
- 그리드 요구는 브라우저·OS 판별(User-Agent)로 걸립니다. Windows의 Edge·Chrome·Whale에서만 요구하고, Opera·Safari(iPad/Mac) UA로 바꾸면 그리드 없이 1080p를 받았다는 보고가 2024년 5~6월에 있었습니다. 다만 2024년 10월 말에는 Safari UA에서 "이 브라우저는 고화질 라이브를 감상할 수 없습니다"로 차단됐다는 보고가 있어, 네이버가 우회를 막는 방향으로 움직이고 있습니다.
- 2024년 8월 27일 변경은 "화질 열화 없는 1080p 원본 화질"에 관한 것이고, 그리드 요구를 없앤 것이 아닙니다.
- **PoC 실측(2026-10-13)**: WebView2(Edge UA)에서 그리드 없이 **720p**까지 재생됐습니다. 480p 제한은 더 이상 아니고, 1080p에만 그리드가 필요한 것으로 보입니다.
- 2026년 10월 현재 같은 정책이 유지되는지는 공식 문서로 확인하지 못했습니다. PoC 실측 결과는 위와 같고, 그리드 설치 후 **1080p 선택 가능 여부만 미확인**입니다([09 PoC 결과](09_PoC_결과.md) P5-b).
- 커넥터와 브라우저가 localhost 서버로 통신한다는 설명은 개인 블로그의 추정이며 확인되지 않았습니다.

**WebView2에 미치는 영향**

| 항목 | 영향 |
|------|------|
| UA 판별 | WebView2는 Windows의 Edge로 판별되어 그리드 설치 안내가 뜸(PoC 확인). 그리드 없이 **720p**까지 재생(PoC 실측) |
| 브라우저 확장 | WebView2는 확장을 기본 지원하지 않으므로 `CoreWebView2Profile.AddBrowserExtensionAsync`로 올림. 네이버 그리드 확장은 **Native Messaging**으로 커넥터와 통신하며, WebView2가 Edge의 `HKCU\Software\Microsoft\Edge\NativeMessagingHosts` 등록을 읽어 커넥터와 왕복 통신하는 것을 PoC에서 확인 |
| UA 우회 | **불허(D-14)**. 서비스 정책 우회이므로 쓰지 않습니다. `UserAgentOverride`는 호환성 조정(R-03) 용도로만 쓰고, 치지직의 그리드 판별을 피하는 값은 넣지 않습니다 |
| 정식 경로 | 네이버가 안내하는 그리드 설치 절차를 WebView2 안에서 그대로 따르는 것이 유일한 방법입니다. (1) 커넥터는 일반 Windows 프로그램이라 그대로 설치. (2) 확장은 Edge 추가 기능 스토어의 공식 CRX("네이버 동영상 플러그인", ID `jedbgfnhnpbfcbplibkacnmiafbojobk`)를 받아 `_metadata` 제거 + manifest `key` 주입 후 `AddBrowserExtensionAsync`로 로드 → **PoC에서 스토어와 같은 ID로 로드 성공**(2026-10-13). (3) 확장은 `chrome.runtime.connectNative("nliveconnector_1.0.0.0")`로 커넥터와 **Native Messaging** 통신(CRX 분석으로 확정). **PoC에서 WebView2가 `HKCU\Software\Microsoft\Edge\NativeMessagingHosts` 등록을 읽어 커넥터와 왕복 통신하는 것을 확인**(2026-10-13, [09 PoC 결과](09_PoC_결과.md) P5-b). 실제 1080p 선택 여부만 남음 |
| 안 될 때 | 치지직은 앱 안에서 720p로 봅니다. 외부 실행 대체는 두지 않습니다(D-07) |

> 참고 자료는 7절에 정리했습니다.

## 4. 핵심 기술 요소

### 4.1 WebView2 구성

| 항목 | 방안 |
|------|------|
| 런타임 | Evergreen WebView2 Runtime (Windows 11 기본 포함, Windows 10은 설치 확인) |
| 환경 | 앱 전체가 `CoreWebView2Environment` 하나를 공유하고, UserDataFolder는 `%LOCALAPPDATA%\MoaView\WebView2` |
| 프로필 | 서비스(·계정)마다 `CoreWebView2Profile`을 분리해서 쿠키 격리와 다중 계정 지원 |
| 인스턴스 | 서비스별로 WebView2 컨트롤 1개를 지연 생성(Lazy)하고, 전환 시 Visibility만 바꿈 |
| 자원 관리 | `ServiceHostManager`가 30초마다 점검해서 비활성 상태로 300초가 지난 서비스는 `TrySuspendAsync()`(`Player.SuspendAfterSeconds`), 활성화될 때 `Resume()`. 살아 있는 WebView가 `MaxAliveHosts`(기본 3)를 넘으면 가장 오래 쓰지 않은 것부터 Dispose(LRU). 값은 DB 설정이 없으면 appsettings.json `Player` 절을 따름 |
| 전체화면 | `ContainsFullScreenElementChanged` 이벤트로 창을 전체화면으로 전환 |
| 팝업 | `NewWindowRequested`: 로그인 OAuth는 앱 안의 대화상자 WebView로, 외부 링크는 기본 브라우저로 |
| 스크립트 | 로그인 페이지는 Provider의 URL 정규식(`IsLoginPage`)과 `NavigationCompleted`·`SourceChanged`(SPA 단계 전환 대응, 0.9초 지연)로 감지하고, `ExecuteScriptAsync`로 `autofill.js`·`logged-out-check.js`를 실행(인자는 `ScriptLoader`가 JSON으로 주입). 로그아웃 판정에는 링크 휴리스틱, `hover-probe.js`, 쿠키 서명 학습(`Login.CookieSignature.{code}`)도 사용. `AddScriptToExecuteOnDocumentCreatedAsync`는 쓰지 않음 |
| 장애 복구 | `ProcessFailed` 이벤트에서 렌더러 실패(`RenderProcessExited` 등)는 `Reload()`, 브라우저 프로세스 실패(`BrowserProcessExited`)는 컨트롤을 다시 만든 뒤 마지막 URL 복원 |

### 4.2 WPF와 WebView2의 Airspace 문제

- WPF의 `WebView2` 컨트롤은 HWND 기반(HwndHost)이라 **WPF 요소를 WebView2 위에 겹쳐 그릴 수 없습니다**(Airspace 문제).
- 영향: 영상 위 오버레이 UI(토스트, 반투명 컨트롤바 등)를 만들 수 없습니다.
- 대응:
  1. 레이아웃 설계에서 WebView 위 오버레이를 쓰지 않음(사이드바는 옆에, 알림 배너는 위에 배치) ← **기본안**
  2. 오버레이가 꼭 필요하면 별도 투명 Popup 창(Topmost 자식 창)을 씀
  3. `WebView2CompositionControl`(WPF용 컴포지션 컨트롤)은 Airspace 문제가 없지만, PoC(P7)에서 비DRM 720p 렌더링만 확인했고 **DRM 보호 콘텐츠 렌더링은 미확인**이라(보호 콘텐츠가 컴포지션 경로에서 검게 나올 가능성 있음) 본 앱은 기본 HWND 컨트롤을 씁니다.

### 4.3 고 DPI / 4K 출력

- `app.manifest`에 `PerMonitorV2` DPI 인식 선언
- WPF 하드웨어 렌더링(`RenderCapability.Tier == 2`)은 PoC에서만 확인했고, 본 앱은 검사하지 않습니다
- WebView2는 기본으로 GPU 가속을 쓰므로 `--disable-gpu` 같은 브라우저 인자를 쓰지 않습니다
- YouTube는 플레이어 영역(뷰포트) 크기로 화질을 정하므로, 4K 화질을 쓰려면 전체화면이나 큰 창이 필요합니다

### 4.5 자동 로그인 정책 (D-09 확정: 쿠키 유지 + 비밀번호 저장·자동 입력)

배경: TVING·Wavve는 일반 웹 브라우저에서도 로그인이 자주 끊기므로, 쿠키 유지만으로는 부족합니다(사용자 경험 기준).

| 계층 | 동작 | 기본값 |
|------|------|:---:|
| 1. 세션 유지 | WebView2 프로필에 쿠키 저장. 세션이 살아 있으면 로그인 없이 바로 시청 | 항상 |
| 2. 만료 감지 | 로그인 페이지 URL, 또는 일반 페이지의 "로그아웃 상태" 표식(로그인 버튼 등)을 감지 | 항상 |
| 3. 자동 입력 | 저장된 ID/PW를 입력란에 채움 → 사용자는 로그인 버튼만 누름 | 켬 |
| 4. 자동 제출 | 로그인 버튼까지 자동으로 누름 | **끔** (계정별 선택) |
| 5. 반복 방지 | 자동 제출 후 다시 로그인 화면이 나오면 실패로 보고, 쿨다운 동안 자동 제출을 멈추고 알림 | 항상 |

- 자동 제출을 기본으로 끄는 이유: 캡차, 2단계 인증, 봇 탐지가 있고, 비밀번호를 바꾼 뒤 예전 비밀번호로 반복 제출하면 **계정이 잠길 수 있기** 때문입니다.
- 반복 방지 규칙(`LoginGuard`, Core에 구현 완료): 자동 제출은 같은 계정에 **10분에 1회**까지(`AutoSubmitCooldownMinutes` 10), 연속 2회 실패하면(`MaxConsecutiveFailures` 2) 해당 계정의 자동 제출을 끄고 "비밀번호 확인" 안내. 입력란이 나타날 때까지 8초 재시도(`FillRetrySeconds`), 제출 후 판정 대기 20초(`SubmitJudgeSeconds`). 값은 appsettings.json `Login` 절
- 사이트 구조가 바뀌면 깨질 수 있으므로, Provider별 셀렉터는 코드가 아니라 **DB 또는 설정 파일로 관리**해서 빨리 고칠 수 있게 합니다
- 로그인 방식별 우선순위:

| 서비스 | 1차 지원 | 2차 (순차) |
|--------|----------|------------|
| TVING | TVING 자체 ID | CJ ONE, 네이버, 카카오 |
| Wavve | Wavve 자체 ID | 네이버, 카카오, T 아이디 |
| Netflix | 이메일/비밀번호 | - |
| 치지직 | 네이버 ID | - |
| YouTube | 쿠키 유지 + Google 이메일·비밀번호 자동 입력(2단계 인증은 사용자가 처리). 이메일을 먼저 받는 2단계 로그인에서 1단계 '다음' 버튼은 비밀번호 제출이 아니므로 자동 제출 설정과 무관하게 누름(의도된 동작) | - |

> 실제 로그인 방식 목록과 화면 구조는 Phase 2에서 휴리스틱(`autofill.js`) 구현으로 대응을 완료했습니다. 사이트별 셀렉터(DB `LoginFormSpecJson`) 확정은 실사용 검증 시 합니다.
